================================================================================
  LOFTR VS LIGHTGLUE: COMPREHENSIVE COMPARISON FOR GPS-DENIED NAVIGATION
================================================================================

This document provides a detailed breakdown of the two feature matching 
architectures tested for matching drone payload cameras (simulated DVS Event 
Cameras) against satellite Reference Maps.

--------------------------------------------------------------------------------
1. ARCHITECTURAL DIFFERENCES
--------------------------------------------------------------------------------

  MODEL A: EfficientLoFTR (Dense Matcher)
  - How it works: Compares broad image patches across coarse-to-fine levels 
    using a Transformer architecture. It does NOT extract keypoints first.
  - Strengths: Highly robust to noise, textureless regions, and severe 
    modality gaps (like color vs. event data). It can "see through" messy data.
  - Weaknesses: Computationally heavy. Runs slower, especially on constrained 
    edge hardware (drone payloads).

  MODEL B: SuperPoint + LightGlue (Sparse Matcher)
  - How it works: A two-step process. First, SuperPoint extracts specific 
    geometric "keypoints" (like sharp corners). Then, LightGlue matches these 
    points between the two images.
  - Strengths: Blazing fast, highly efficient, and adaptive. It drops 
    unmatchable points early to save compute time.
  - Weaknesses: "Brittle" to modality gaps. If SuperPoint cannot find corners 
    due to weird noise (like RAW event data), LightGlue has nothing to match.

--------------------------------------------------------------------------------
2. EXPERIMENTAL RESULTS (MEAN CONFIDENCE SCORES)
--------------------------------------------------------------------------------

  TEST 1: RAW RGB Map vs RAW Event Frame (No Pre-Processing)
    - LoFTR:      0.3281
    - LightGlue:  0.1704 (12 matches found)
    >> Verdict: LOFTR WINS. 
       LightGlue's keypoint extractor completely collapsed trying to read 
       the red/blue pixel noise of the RAW event frame. LoFTR survived 
       because it matches broad patches.

  TEST 2: Spatial Gradient Map vs Grayscale Event Frame
    - LoFTR:      0.4166
    - LightGlue:  0.3844 (401 matches found)
    >> Verdict: TIE. 
       By extracting the geometric edges (gradients) from the RGB map and 
       removing the red/blue polarity from the Event frame, we successfully 
       "bridged" the modality gap. Both models performed excellently.

  TEST 3: Spatial Gradient Map vs RAW Event Frame
    - LoFTR:      0.4109
    - LightGlue:  0.4178 (499 matches found)
    >> Verdict: LIGHTGLUE WINS (Slight Edge).
       Interestingly, leaving the event frame colored while matching against 
       a spatial gradient map yielded the absolute highest confidence score 
       for LightGlue across all event data tests. 

  TEST 4: Grayscale Map vs Grayscale Standard Drone Frame (Baseline Test)
    - LoFTR:      0.4648 (908 matches found)
    - LightGlue:  0.3661 (402 matches found)
    >> Verdict: LOFTR WINS.
       When tested on a standard, high-quality photograph (no event camera), 
       LoFTR dominated in both confidence and total matches.

--------------------------------------------------------------------------------
3. CONCLUSIONS & RECOMMENDATIONS
--------------------------------------------------------------------------------

  A. When to use LOFTR:
     Use LoFTR if the drone's compute payload can handle it AND you want maximum 
     resilience. If your preprocessing pipeline breaks, or you encounter strange 
     textures (like RAW Event data), LoFTR is much less likely to completely 
     fail. It provides the safest, most robust match.

  B. When to use LIGHTGLUE:
     Use LightGlue if you are strictly constrained by compute/battery on the 
     drone AND you can guarantee a strong preprocessing pipeline. As long as 
     you use the Spatial Gradient Modality Bridging (Test 3), LightGlue performs 
     identically to LoFTR but operates at a fraction of the computational cost.

  Final Verdict:
  For a high-speed, edge-compute drone using an Event Camera, LightGlue paired 
  with Spatial Gradient pre-processing (Test 3) is the optimal configuration for 
  balancing high-accuracy navigation with low latency. However, if dealing with 
  unprocessed RAW camera feeds, LoFTR is mandatory.

--------------------------------------------------------------------------------
4. ADDENDUM: SUPERGLUE INTEGRATION
--------------------------------------------------------------------------------

  We subsequently integrated and tested the original SuperGlue architecture 
  (the predecessor to LightGlue) using the same outdoor weights and tests.


  SuperGlue Sanity Check (Control Test):
  - We ran a self-matching test (Reference Map vs Reference Map).
  - Matches: 720
  - Mean Confidence: 0.9740
  - Conclusion: The SuperGlue pipeline is fundamentally sound. The drop in 
    confidence seen in tests 1-4 is purely due to the extreme difficulty of 
    cross-modality matching, not an error in the deployment code.

  SuperGlue Results (Mean Confidence):
    1. RAW RGB Map vs RAW Event Frame:              0.2684 (6 matches - Total Failure)
    2. Gradient Map vs Grayscale Event Frame:       0.4474 (337 matches)
    3. Gradient Map vs RAW Event Frame:             0.5019 (314 matches)
    4. Grayscale Map vs Grayscale Drone Frame:      0.6003 (301 matches)

  SuperGlue Analysis:
  - SuperGlue achieves the absolute highest confidence scores on valid matches 
    (reaching 0.5019 on Event Data and 0.6003 on Standard Data).
  - However, it extracts significantly fewer total matches than LightGlue 
    (314 vs 499 on Event data).
  - Like LightGlue, it relies on SuperPoint and thus completely fails on 
    unprocessed RAW Event data (6 matches).
  - SuperGlue is slightly slower and more compute-heavy than LightGlue, as 
    it lacks the adaptive stopping mechanisms of its successor.

  Final Verdict update: LightGlue remains the optimal choice for the drone 
  due to its faster inference and higher total match count, even though 
  SuperGlue boasts slightly higher mean confidence on the points it does find.

5. C++ ENGINE DEPLOYMENT & LATENCY BENCHMARKS (SP-SLAM3)
--------------------------------------------------------------------------------

  We deployed the winning LightGlue architecture into a C++ SLAM engine 
  (SP-SLAM3) using LibTorch for real-time visual odometry.

  Python Benchmark (Ideal Scenario):
  - Total Latency: 92.59 ms per frame (~10 FPS)
  
  C++ Engine Initial Port (Unoptimized):
  - Extraction Latency: ~331 ms per frame
  - Matching Latency: ~130 ms per frame
  - Issue: The Non-Maximum Suppression (NMS) during SuperPoint feature 
    extraction was performed on the CPU using a nested for-loop over the 
    massive 4K heatmap, creating a massive memory transfer bottleneck.

  C++ Engine Final Port (FP16 & Multi-Threaded):
  - Extraction Latency (Dual Concurrent Images): 38.8 ms
  - Matching Latency (LightGlue FP16): 127.0 ms
  - Total Real-Time Latency: 165.9 ms per frame (~6 to 7 FPS)
  - VRAM Consumption: ~1.4 GB
  - Solution: Re-wrote the NMS logic natively using LibTorch max_pool2d 
    on the GPU (yielding 12x speedup in extraction), exported the models 
    to Half-Precision (FP16) to leverage Tensor Cores, and wrapped the 
    inference loop in C++ std::thread to extract multiple frames 
    simultaneously, masking extraction latency entirely.
